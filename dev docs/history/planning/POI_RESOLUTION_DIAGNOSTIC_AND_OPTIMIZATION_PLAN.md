## 1. 结论与范围

本包围绕五个问题：重新搜索后收起、自动搜索与手动搜索结果不一致、景区正式名称扩展、景区与内部景点竞争、市县行政区域的地图代表点。保留 Source/Snapshot/Segment/Claim/Evidence 身份、作者态度与人工确认边界，不通过降低全局分数阈值解决问题。

| 用户判断 | 排查结论 | 拟采用规则 |
| --- | --- | --- |
| 推荐市县可匹配到政府驻地 | 作为区域代表坐标合理；政府机关与行政区域不是同一旅游实体，且当前冻结契约不支持此投影 | 保留 Destination 身份，另存同级政府驻地代表点；地图显示区域名称和“政府驻地代表点”，不把原推荐改成推荐政府机关 |
| 景区名加自然保护区、国家森林公园、风景名胜区等可自动匹配 | 在同一实体、同一地域、类别兼容时合理；不能任意删后缀或以名称包含作为充分条件 | 增加受控正式名称等价规则，保留全部原名、候选名与判定理由 |
| 游客接待中心等也可自动定位 | 可作景区定位入口，但通常不是景区本体 | 有唯一、可信景区归属时使用入口代表点，明确坐标用途；多入口或归属存疑仍复核 |
| 景区内部景点不应与景区本体争分 | 已由目标样本与代码证实 | 先判定目标层级，再在同层级候选之间比较；保留子景点用于查看和独立地点匹配 |
| 同名手动搜索有结果，说明自动搜索需排查 | 成立，但不能直接归因为高德漏搜 | 先区分未发起、成功为空、失败、部分成功和候选被门禁拦截；再对比查询参数与响应 |
| 点击重新搜索就收起 | 源码已证实搜索成功会主动关闭输入框 | 保留输入与展开状态、就地更新候选、提供加载/成功/空结果/失败反馈 |

证据范围：用户提供的截图、当前源码、目标笔记只读 API 和现有 SQLite 只读查询。未点击生产搜索/确认按钮，未发起高德或模型请求，未重新运行视频；未进行 Browser 动态复现。源码路径与函数名为定位依据，后续行号可能变化。

## 2. 已证实的问题

### 2.1 搜索成功主动关闭表单

[PlaceReviewCard.tsx](../../../frontend/src/features/places/PlaceReviewCard.tsx) 的 `search.onSuccess` 执行 `setEditing(false); refresh()`。因此成功返回后输入框消失是现有逻辑的直接结果；尚未动态证明用户描述的“收回去”是否还包含候选 details 折叠或页面滚动跳动。

组件当前未展示 search 的失败消息、结果数量或成功提示；现有 [组件测试](../../../frontend/src/features/places/PlaceReviewCard.test.tsx) 仅覆盖确认后地图入口，没有搜索后保持展开的断言。重新搜索会更新 `suggested_name`、候选缓存并递增 revision，不能为复现而把生产 POST 当作只读操作。

### 2.4 跨 Segment 引文校验口径不一致，已有具体样本

抽取阶段 `_candidate_has_evidence` 去除空白后直接拼接片段；[evidence_trace.py](../../../backend/src/zhijian/services/evidence_trace.py) 的 `evidence_trace` 则使用换行拼接 `corrected_text or text`，要求原 quote 是该字符串的精确子串。两者口径不一致，可能把真实跨片段原句误判成证据无效。

对该视频7条带 SOURCE_EVIDENCE_INVALID 的 EXTRACTED 记录做只读校验（上述6条加九龙瀑布）：片段均存在、ID无重复、每条只涉及一个 Snapshot，Snapshot.source_id 与 VideoAsset.source_id 一致且 video_asset_id 绑定正确；**7条 quote 均不能匹配插入换行的文本，却都能精确匹配直接拼接的文本，无需修改任何汉字或标点。**这证实了这些当前记录上的拼接差异；不等于已重放原历史执行，也不证明全部引文语义归属正确。

修复应统一可追溯的跨片段拼接契约，而非删除 evidence gate。需进一步验证片段顺序、连续性、原文/校对版本和字符位置映射；不得通过去掉任意标点、改字、近似语义或跨来源拼接来“修好”证据。

### 2.5 自动与手动入口确实不同

| 入口 | 当前行为 |
| --- | --- |
| 自动解析 | 先态度/证据门禁，按 suggested/name/raw/aliases 与地域组合搜索，合并候选后评分和决策；最多5组文本查询，可追加附近搜索 |
| 待复核卡重新搜索 | 直接以输入文字和 mention.city_hint 搜索；不执行相同的自动证据/态度门禁，也不调用统一排名；更新候选与 suggested_name，仍需用户确认 |
| 地图单独添加搜索 | 使用输入文字全国搜索，按名称包含和长度等排序，不等于视频自动解析路径 |

手动入口允许用户在审阅证据后补充定位，不应把这一差异本身视为漏洞，也不能反过来用手动结果绕过自动确认条件。当前人工重新搜索只替换候选，旧 reason/decision 仍可能留存，页面可同时显示旧阻断理由与新候选分数。需要把“自动判定原因”和“最近一次手动搜索结果”分开记录、展示。

定位：[router.py](../../../backend/src/zhijian/api/router.py) 的 `search_place_review`、`search_map_pois`；[video_support.py](../../../backend/src/zhijian/services/video_support.py) 的 `resolve_mentions_with_amap`、`_rank_poi_candidates`、`_poi_queries`。

## 4. 拟实施规则与数据契约

### 4.1 统一搜索事实，保留自动/人工权限差异

提取共用查询计划、候选标准化与排名服务。显式传入 AUTO / MANUAL 模式：AUTO仍先验证来源和态度；MANUAL可搜索，但搜索不等于自动确认。原始输入不变，建议名与查询名分别保存。既有人工确认、删除墓碑和拒绝状态不被重新解析覆盖。

每次搜索记录有界的 `resolver_version`、模式、查询参数摘要、地域来源、缓存状态、耗时、候选ID与阶段结果：未执行、成功有结果、成功为空、部分成功、Provider失败；保留阻断原因。字段名称属方案，实施时与既有日志/Artifact契约对齐，不新增无界日志或明文凭据。缺失旧记录显示“历史请求信息不完整”，不补造请求轨迹。

查询顺序：完整名称+可信当前城市 → 同地域可信别名/正式名称 → 必要时全国召回 → 有已验证锚点时附近检索。全国召回不抹去已有城市冲突；候选地址不能自己充当原文地域证据。只在成功为空或候选覆盖不足时扩大查询，不因429/QPS/认证失败连续重试。文本查询沿用最多5组预算，扩展分页/附近检索须纳入统一预算；保留本机共享1.1秒间隔、冷却、去重和Key隔离。

单查询异常保留已成功候选并标明覆盖不完整；若失败查询可能改变身份判断，默认不自动确认。显式重新搜索可设计为绕过该次查询的空结果缓存，不清全局缓存、不绕过QPS门禁。空结果与正常候选采用独立TTL，具体值由离线/受控实测确定。

### 4.2 正式名称等价与景区层级

将关系区分为本体等价名、内部景点、入口设施、其他同名实体和未知；不得仅因共享前缀、同类别或距离近就认定父子关系。优先使用Provider可靠关系字段（实际可用性待验证），否则要求规范本体名、明确分隔后缀、行政区一致及地址/空间等辅助依据共同支持。

正式后缀规则仅用于保留核心专名后的受控匹配，如“玉龙雪山”与“玉龙雪山国家级风景名胜区”。自然保护区、国家森林公园、风景名胜区并非总是同一实体；核心名相同但法定范围/位置不同仍是竞争候选。“西湖”“古城”等泛称不得因后缀扩展获得强确认。

提及本体时，明确子景点不参与本体候选的分差计算；提及具体子景点时，父景区不能取代该子景点。本体缺失时不得随便挑一个子景点充当本体。比较同层级的不同本体，保留候选关系和排除原因；分差计算保留未封顶评分，单候选不意味着已证明唯一。

保持来源、态度、地域、类别、坐标、详情一致性门禁。针对玉龙雪山，先消除子景点竞争，再从同版本原句/内容单元取得可核验地域；无此依据时保持“待核地域”，不把全国搜索的第一个结果视为足够证据。离线报告应分别展示“排名修复”和“自动确认是否放行”。

### 4.3 行政区域政府驻地代表点

此项是产品能力扩展，**与当前 [冻结清单](../../REGRESSION_AND_CHANGE_GUARD.md) 中 AREA_RESOLVE 只建 Destination 的规则存在待修订边界**，不能按普通POI改名修复处理。后续实施先冻结扩展契约；本轮不修改该冻结规则。

方案保留 [Destination模型](../../../backend/src/zhijian/db/models.py) 与原 Mention 的区域身份，使用现有 center/adcode/metadata 评估承载代表点：存储代表政府POI ID、名称、GCJ02坐标、行政层级、完整上级行政链、定位用途、验证来源与版本。原区域名称与作者推荐内容不变，不生成“作者推荐去政府办公楼”的证据。

只有作为实际推荐目的地的市/县/区（自治州等同级目的地区域纳入显式映射）才进入该路径；背景地域、REFERENCE_ONLY/SKIP、整体负向/存疑地点不进入自动驻地查询。需匹配本级人民政府驻地，排除街道办、下级政府、政务服务中心、旧址和名称相似办公机构；简称或同名区县必须靠上级行政链消歧。不能证明唯一时保留区域待定位，不退而匹配省政府。

当前 Destination 唯一键仅含 scope_type+canonical_name，存在同名行政区合并风险；正式落地前必须评估行政编码/上级地域身份约束。不能为了避免迁移，把新身份强塞旧键。需要Schema变化时新增Alembic迁移并单独取得迁移授权；现有数据只读预览，不批量合并或改写。

地图需新增区域代表点投影/类型和入口，保留原坐标用途展示；不得冒用 Place ID、把 Destination伪装成已确认旅游POI。聚合、筛选、详情、导航和可见性均纳入验证。涉及API/地图的能力边界应作为独立子工作包交付。

### 4.4 游客接待中心与入口代表点

原文明确推荐接待中心时按该实体匹配；原文推荐景区而仅找到中心时，只可在景区身份与中心归属已验证、入口唯一且可访问性信息无冲突时自动选为定位入口。景区名保持，另存代表POI身份、用途和来源，详情/导航明确“定位至游客中心”。

多个中心、东西门、不同道路入口不自动猜测。景区本体、子景点与入口用独立身份/关系，不能把中心POI ID绑定为景区本体身份；若现有Place唯一键无法承载，先做数据契约设计和迁移评估，不默认无迁移可实现。用户“能匹配到即可”的目标据此收敛为“关系明确时自动定位”。

### 4.5 搜索交互

搜索成功后保留输入框、关键词、焦点及候选展开状态，就地更新结果并显示数量；等待时显示“正在搜索”并防重复提交，出错显示可操作原因，成功为空与失败明确区分。只有用户点击取消/收起才主动关闭搜索。revision冲突先刷新并提示，禁止静默重试覆盖。

将旧自动判定原因与最新手动搜索反馈分开；仍保留用户显式确认地点位置。PC与Mobile保持共享控件/Token及最小点击区域，布局不跳回页首，不因缓存刷新卸载整个复核卡。长候选列表、空结果与错误提示均应可读。
