# 视频地点推荐态度贯通实施计划

日期：2026-10-26（原计划）；2026-10-27已获授权并完成源码与隔离验证，归档用于设计追溯。实际能力、发布与未闭环项分别以当前实施状态和带日期生产快照为准；本正文中的“本次仅规划/未来授权”保留为原写作时边界，不再作为当前待办。生产根实际搬迁、物理故障和真实模型质量未验证。

## 1. 目标与已明确的产品边界

用户要求：视频说“A 景点值得去，但别坐游船”时，只在 **A 景点值得去** 这一层判断推荐；“别坐游船”放在 A 景点介绍中。游船、菜品、天气、时节、费用和局部玩法不因评价而升级为独立推荐对象，也不单独创建地点、地图点或审核任务。

地点仍按现有真实地理实体识别规则抽取。原文明示另一个具名景点时，它可以是独立地点；不能因一句“游船不好”虚构一个游船 POI。整体态度必须是作者对该地点是否值得到访的明确意见，不能由“风景不错”“门票贵”“某个项目不好”等局部事实自行推导。

本包目标：同一条地点态度从转写证据进入语义提取、地点提及、笔记、POI 复核、地图与详情后保持一致；确认位置不改变作者态度，多来源分歧不被静默覆盖。作者态度与用户“喜欢／不喜欢／想去／去过”等个人状态独立。

### 1.1 核心验收条件

1. “A 值得去，但别坐游船”：A 为推荐；游船限制完整出现在 A 介绍/提醒中；无新增游船地点、独立态度卡片或审核任务。
2. “A 不值得去，B 值得去”：A、B 各自归属正确；A 进入不推荐复核，自动高德请求及自动创建地图点均为零，B 走既有正常流程。
3. 不推荐地点经过用户显式搜索并确认 POI 后，仍显示“作者不推荐”；确认操作不生成正向推荐，也不改用户偏好。
4. 同地点有互相矛盾的整体态度时，保留双方证据并显示分歧；处理结果不受候选输入顺序影响。
5. 笔记、地点卡片、地图单点/聚合成员和详情使用同一份后端态度投影；不得出现后端为不推荐、界面却作为正向推荐的情况。
6. 旧记录缺少可靠态度证据时显示“态度未明确”或必要的复核提示；不批量改历史、不自动重跑、不把默认值当作推荐。

## 3. 产品判定规则

| 原文示例 | 地点整体态度 | 地点介绍中的内容 | 自动处理 |
| --- | --- | --- | --- |
| A 值得去，但别坐游船 | 推荐 | 游船不建议体验及原文理由 | A 正常处理；游船不单独建对象 |
| A 值得去，但下雨别来 | 推荐 | 雨天限制；已有时间窗口能力可保留该条件 | 不降为地点不推荐 |
| A 的游船不推荐 | 未明确 | 游船限制 | 不据此断定 A 推荐或不推荐，按既有实体/POI规则处理 |
| A 不值得去，游船倒不错 | 不推荐 | 局部体验评价完整保留 | 不被局部优点覆盖；人工复核 |
| A 可以顺路去，没必要专程 | 可选 | 顺路/专程条件与理由 | 不归入明确推荐或整体不推荐 |
| A 只适合带孩子去 | 有条件的地点意见 | 保留人群条件；无明确推荐措辞不擅自补推荐 | 不将条件删除后输出普遍推荐 |
| 不少人说 A 不好，我觉得值得去 | 作者推荐 | 他人意见按转述保留 | 不把转述直接当作者自相矛盾 |
| 我去年不推荐 A，改造后现在值得去 | 作者明确改变意见 | 时间、变化原因及旧意见保留 | 只在来源明确表达修正时采用当前意见 |
| A 值得去；另一段又说 A 不值得去，无解释 | 存在分歧/待复核 | 两段意见并列 | 不按最后一句或首次出现覆盖 |
| 只提到 A，或拿 A 作比较 | 未明确/背景 | 保留提及语境 | 不凭出现次数、主角身份或 POI 已确认推导推荐 |

“推荐／可选／不推荐／态度未明确”描述来源意见，不生成系统评分。条件是介绍内容的一部分；涉及安全、封闭或明确禁入的提醒仍按现有规则优先显示，不能因整体推荐而被隐藏。正文过长允许展开，但关键否定和限制不得只剩正向摘要。

## 4. 数据与证据设计

### 4.1 存储边界与字段

复用 `PlaceMention.visit_intent` 的现有枚举 `RECOMMENDED / OPTIONAL / NEUTRAL / NOT_RECOMMENDED / NOT_APPLICABLE`。整体态度附着于具体来源、Note Version 和 PlaceMention；不在共享 Place 上写一个覆盖所有视频的唯一推荐值。

拟增加可校验的 `recommendation_evidence` 元数据，优先存于已有 Artifact/PlaceMention JSON 容器，配套严格的应用层 Schema 与版本号。字段至少包括：`schema_version`、`assessment_status`（VERIFIED / NEEDS_REVIEW / UNKNOWN）、`statements[]`（原始态度、逐字引文、Segment IDs、明确的主体 Entity ID、说话者归属、原文存在时的条件/时间/修正关系）及 `reason_codes[]`。这里的 VERIFIED 仅表示程序证据检查通过，不代表人工或真实模型质量验收。

局部玩法、菜品、天气和费用继续复用 `WARNING / AUTHOR_OPINION / HIGHLIGHT` 等 Claim 与地点介绍字段；为防止它们参与整体态度聚合，只增加必要的内部范围标识 `PLACE_OVERALL / LOCAL_DETAIL / UNCERTAIN`。范围标识用于归属校验，不产生局部对象、独立推荐等级或新的用户操作。

来源 ID、Note/Transcript 版本、Mention/Entity/Claim 身份沿用现有绑定，禁止用名称近似跨城合并。态度引文与地点名称可位于不同但已验证绑定的片段；每个态度必须有自己的证据，不能用仅含地点名称的引文证明“推荐”。

不默认新增数据库表/列；若实施发现现有 JSON 容器无法满足查询和审计要求，先补充具体 Schema 方案与迁移影响，再走追加 Alembic migration 和独立生产迁移授权，禁止修改历史迁移。

### 4.2 提取、校验与失败处理

1. 在现有证据地图调用中一并提取整体态度和局部详情，复用现有 Worker、模型路由、参数快照及预算；不默认新增一轮模型调用。
2. 服务端核验 Segment 属于本包/版本、引文逐字成立、主体 Entity 有效、态度枚举合法；共享片段以 `subject_entity_ids` 绑定，不向同段全部地点广播。
3. 整体态度必须有 `PLACE_OVERALL` 证据。只有局部负向详情时，既不能判地点不推荐，也不能因没有整体否定而判推荐。
4. 否定词规则只作疑点检测：核对否定对象、条件、转述、双重否定及前后修正；“不是不推荐 A”不得被关键词直接判负向。规则无法确认时输出 NEEDS_REVIEW，不伪装成已理解语义。
5. 标签与证据疑似冲突、同主体整体正反冲突或关键态度证据不完整时保留原文并复核，暂停该提及的自动 POI 确认/新增地图点。没有态度的普通有效地点继续既有流程，但不进入明确推荐集合。
6. 无效 ID/伪造引文拒绝形成有效态度；有效原始片段继续保留。技术失败按既有重试/降级契约处理，不吞掉不推荐内容来换取成功状态。

### 4.3 合并、缓存和重放

同地点候选合并先合并去重后的证据声明，再计算展示态度，不直接继承第一条/最后一条候选的 `visit_intent`，不按置信度最大值覆盖另一条意见。相同输入集合以任意顺序输入须得到一致结果。

同来源的转述、适用条件或明确时间修正能够解释差异时保留解释；无法解释的整体正反意见输出 CONFLICT 展示状态。跨来源无论发布时间先后，正反意见都按来源并列；不投票产生“官方推荐”，也不把条件不同的两条意见必然判作冲突。CONFLICT 属于派生聚合状态，不强塞进旧 `visit_intent` 枚举。

Prompt、Artifact 证据结构与派生判定各有版本标识；仅失效受影响阶段缓存，防止旧缓存被当成具备新证据。显式重跑生成所属 Note 的新版本，旧版本不回写，重放幂等且不重复生成审核项、Claim 或 Marker。任务、模型、证据、缓存隔离沿用现有身份规则。

## 5. 下游贯通与展示

### 5.1 笔记与地点介绍

`_place_evidence_index`、`_pack_place_evidence` 及所有实际使用的归纳/回退路径传递整体态度、校验状态与对应证据；每个分包只使用本包可验证的引文。章节按地点组织：A 的推荐结论、看点、游船限制均在 A 章节内，比较和归属不明内容独立保留。

生成后检查整体态度和关键限制是否保留、是否错绑地点；明确不推荐不得写进正向推荐摘要。无法确认覆盖时保留明确标注的原文/结构化提醒并报告既有 HYBRID/质量告警，不宣称模型完整完成。检查不能仅靠检测输出是否出现“不推荐”三个字，应核对对象、证据与极性；受限规则无法判定的情况进入复核。

地点介绍保留局部负向内容；例如“A 值得去；游船不建议乘坐，原因……”。提醒展示沿用现有正文/卡片，不建立“游船：不推荐”的平级地点卡。地图短摘要不能只取正向半句而抹掉重要限制，完整原句与视频时间链接始终可达。

### 5.2 后端统一投影与 API

建设一个共享的只读态度投影，供视频地点 DTO、审核 DTO、PlacePreview/PlaceDetail、地图单点及聚合成员复用。建议结果为 `recommendation_summary`：`status`（RECOMMENDED / OPTIONAL / NOT_RECOMMENDED / CONFLICT / UNKNOWN）、`review_required`、`source_opinions[]`、证据来源和版本、必要的条件摘要。前端只负责标签与排版，不再从自然语言或 POI 状态重复判定。

视频页面使用当前 Note Version 内的态度；共享地点页面按各关联 Note 的当前有效版本聚合，不把旧版本重复计作独立来源。旧版本阅读仍显示该版本的意见。排除 USER_REJECTED/SUPERSEDED 等无效提及；过期转写仍可显示已保存的原态度与证据不可回放提示，不把过期当作态度改变。

整体负向证据必须通过独立通道进入态度投影，即使 `experience_projection` 为生成推荐体验而过滤了该提及，也不能从聚合结果中消失。知识项中的作者意见和新投影需去重显示，并保留现有冲突信息。

### 5.3 人工复核、确认和地图

审核卡明确区分“作者不推荐”“意见有分歧”“态度证据待核对”。保留原句、上下文和跳转；不推荐仍不自动搜索高德，用户可显式搜索并确认地点位置。按钮使用“确认地点位置”等准确文案，不能暗示确认了推荐意见。

确认 POI 不修改 `visit_intent` 或态度证据。当前包不新增人工改写作者态度功能；确认后仍显示相同态度标签，地图浮窗/详情/视频地点列表一致。用户个人偏好按钮照常使用，不能反馈覆盖作者意见。

保留现有“人工确认后可上图”的行为，地图仍展示地点收藏和证据，不改成仅推荐地点地图。负向或分歧地点被显式确认上图后必须可辨识；推荐摘要/推荐分组只接受具备有效正向证据的地点。OPTIONAL、UNKNOWN 和 CONFLICT 不冒充明确推荐，既有地点也不因新规则被自动隐藏或删除。

聚合仍按原地图交互列出准确成员；各成员带自身态度，不能用共同看点抹掉成员负向意见。混合态度的聚合不输出“这些地点都值得去”等整体推荐。地点级标签使用文字配合既有视觉令牌，不能只依赖颜色。

## 6. 历史兼容与安全边界

历史结构化态度仍可只读展示；缺少新证据状态时标识为旧提取记录，不能升级为已重新校验。仅凭原文和确定绑定可做保守只读投影，无法判断则 UNKNOWN/待复核。禁止在页面读取时调用模型、补写历史态度或自动修改历史 Marker；同一新负向来源关联已存在地点时补充来源分歧，不删除其他来源的正向证据。

新旧 API 字段采用可选字段和明确 UNKNOWN 默认值，避免前后端发布短暂不一致时显示成推荐。不提供旧版接口作为绕过审核门禁的路径。保持修订号冲突保护、人工确认审计及跨页面刷新。

只处理本计划工作包；不扩展自动行程、推荐分数、独立玩法库或批量历史治理。长任务进入 Worker；Secret、Source/Snapshot/Segment/Claim/Evidence、Note/Version 及 raw/corrected Transcript 边界保持。`dev docs/export-evaluation-doc/` 持续仅保留本地，不纳入未来提交或推送。

## 8. 验证矩阵与完成标准

| 样例/场景 | 必须验证的结果 |
| --- | --- |
| A 推荐 + 游船不推荐 | A 推荐；介绍保留游船限制；无游船地点/独立审核 |
| A 推荐 + 天气/菜品/费用负向 | 不误判地点整体负向；限定对象、条件完整 |
| A 不推荐 + B 推荐，同一 Segment | 态度和 Claim 不串绑；A 自动 POI 0，B 正常 |
| 只有局部评价/仅提及/比较 | 地点整体 UNKNOWN 或原有背景状态；不默认推荐 |
| 顺路可去/人群条件 | 保留可选或条件，不升级为普遍推荐，也不简化为全盘否定 |
| 双重否定、转述、明确改口、无法解释的正反意见 | 不依赖单个否定词定案；可解释差异保留语境，不能解释则复核 |
| 多候选/跨包重复，正反输入顺序互换 | 聚合结果一致；所有有效原句可追溯，旧缓存不冒充新结构 |
| 无效 Segment、伪造引文、错误主体、未知枚举 | 不生成有效推荐；保留可追溯失败/复核原因 |
| 不推荐地点人工确认位置 | 后端态度原值不变；卡片、地图、详情仍显示作者不推荐 |
| 同地不同视频意见相反 | 各来源意见并列，聚合显示分歧，不投票、不按时间覆盖 |
| 既有已确认/已隐藏地点、新负向来源、旧 Note 版本 | 不自动隐藏/删除/恢复，不重复计数，不回写历史版本 |
| 分包、fallback、HYBRID、转写过期 | 关键否定不消失；不能核对时明确标识边界 |
| 地图混合态度聚合、页面刷新和个人偏好操作 | 成员态度一致；聚合不泛化推荐；用户偏好不改变作者观点 |

开发中只跑相关目标测试，扩展现有 `test_place_experience.py`、`test_video_semantic_poi.py`、`test_poi_note_structure.py` 和相关 API/前端测试；仅为未覆盖且有实际风险的行为新增用例。代码工作包结束后运行一次全量后端/前端及必要 Lint、类型和隔离构建；失败或后续改动只补相关验证。验收必须包含零外部调用断言、POI 确认前后字段对比、候选顺序互换及历史不变性检查。
