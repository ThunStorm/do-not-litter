# 时节缺陷修复与Token模块分析（2026-10-29）

本轮修复上一轮三个复现缺陷；不切换生产历史，不修改原审查证据。本轮没有新增模型调用。源码修复与后续Token优化方案分别记录，尚未把候选压缩格式应用到生产Prompt。

## 修复与验收

- 所有识别行中的否定/关闭/维修等限制参与质量门禁，小字限制无法可靠归属时NEEDS_REVIEW，不能被大字推荐覆盖。cover_contexts也复核质量，不能靠调用方READY绕过。
- 冲突检查使用显式月份/季节/日期范围交集，支持跨年；无明确日历范围的假期保持不猜月份的保守处理。该案例内存副本加入冬季限制后，8月仍为RECOMMENDED。活动用途的原门禁保留。
- 视觉关闭时，OCR键不依赖视觉策略/Profile；视觉开启时只纳入推理相关字段，不纳入探测/名称等运维元数据。下游语义身份按图像和已认可内容生成，不因未触发视觉的配置变化失效。显式force_regenerate仍可重算，新的解析版本有一次正常失效。
- 实际extract_cover_text路径复验：相同输入命中；探测记录变化仍命中，OCR执行从旧行为2次变为1次，下游身份保持一致；视觉开关变化但未发生视觉推理时，语义身份仍一致。
- 后端全量807项通过，前端全量/ESLint/TS/隔离构建通过，Ruff/diff检查通过。反例与JUnit在data/benchmarks/temporal-repair-20261029。未把测试通过数当作所有视频/型号的语义毕业证明。

## 优化方案与本案例离线测量

同一个NOTE_REDUCE包、相同事实和配置，只改序列化布局；以项目字符/2启发式估算，不是供应商分词器或费用实测。

| 方案 | 一包输入估算Token | 比当前减少 | 相对无主题基线增量 |
| --- | ---: | ---: | ---: |
| 当前完整主题资料 | 11,026 | 0 | 3,659 |
| 每包共享context注册表，地点仅引用 | 9,357 | 1,669（约15.1%） | 1,990 |
| 共享表再精简模型投影 | 8,371 | 2,655（约24.1%） | 1,004 |

优先实施共享注册表+精简模型投影：保留source_kind、时间原词、用途/活动/范围、原句/Segment与成员关系、局部例外；bbox、图片哈希、引擎/审核/追溯字段保留在原始Artifact与UI中，不在每个地点重复送给文字模型。可消除约72.6%的本案例主题输入增量，但不是全部增量都可安全删除。新格式须同步请求编译器/短ID还原/Prompt，验证否定、局部限制和来源跳转再发布。

其次合并重复Prompt规则，保持完整系统守卫；减少模型被要求生成的机器字段，能从程序确定的身份/校验字段由后处理填充；时节依据可由已验证投影固定展示，减少LLM再次判断和复述。任何输出结构精简都必须保留主体/证据/例外，不能把输入压缩当成质量已经通过。

再分开“语义待核”和“临时请求失败”：多月份/主体不明在输入未变时反复推理通常没有收益，可按内容版本保持待核缓存；只有超时等临时失败采用TTL/退避。下游文本身份可进一步聚焦已认可语义，避免无效主题或bbox轻微变化重跑Map；这部分尚未量化，必须保留否定/范围/质量变化的失效条件。

维持视觉按需而非每次调用；本轮缓存修复优先消除了不必要的重复调用。优化格式落地后再做一次受控、同模型/参数/输入的真实A/B，分别记录实测/估算/未知以及Provider前缀缓存，才可计算实际费用或额度节省。先前REMOTE 72,689/38,321、LOCAL 9,778/2,949是整轮开发验收总账，不是单次视频基准。
